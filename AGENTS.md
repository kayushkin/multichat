# About multichat

## What it owns

`:8402` (`PORT`), unit `multichat-server.service`, on localhost only. The unified inbox over a Synapse Matrix homeserver (`127.0.0.1:8008`) with six **mautrix** bridges in Docker — **whatsapp, telegram, signal, meta** (Facebook Messenger; the current bridge no longer carries Instagram), **discord** and **slack**. The Go API only ever talks to Synapse's client API and speaks no platform protocol of its own. **This is the way agents read and message people on Discord**; `si` still carries its own older Discord feed for inber, and matterbridge is not involved. **Its web UI is dash**: bridge-ui's Messages pages (Conversations, Search, Contacts, Discord) reach this API through dash's proxy. The old site at `chat.kayushkin.com` — a React app under `frontend/` plus `/api` and `/ws` on the internet — was switched off on 2026-09-28; its code is in git history, and `deploy.sh` removes its nginx site wherever it is still installed. `docs/api.md` is the route table; `docs/llm-bridge-integration.md` records the design choice — Option D (the bus for inbound events, direct HTTP for sends, no outbound over the bus) plus Option C (the MCP tool surface for agents).

## Where this prompt lives

These sections are stored in agent-store as a project prompt collection and rendered, with identical text, to `AGENTS.md` and `CLAUDE.md` at the root of this repo, so that whichever file a harness reads it gets the same thing. Edit them on dash `/files`, or edit either rendered file: the 15-minute scan carries the edit back into the sections and out to the other file. The host prompt keeps one row for this repo with only what an agent elsewhere needs.

# How it works

## Reading and sending messages

Every route below is under `localhost:8402/api` (and, for the subset dash forwards, `dash.kayushkin.com/api/multichat`) and needs `Authorization: Bearer $MULTICHAT_TOKEN`.

- **Find a conversation**: `GET /conversations` lists joined rooms with `room_id`, `name`, `platform`, member ids and the last message, newest first. ⚠️ A room is listed only when a bridge puppet is a member, so a Discord or Slack channel nobody has posted in since it was bridged is missing from the list. It still works by its `room_id`, which the bridge's management room or Synapse's `joined_rooms` gives you.
- **Read**: `GET /conversations/{room_id}/messages?limit=50` returns `messages` (each `event_id`, `sender`, `sender_name`, `body`, `msg_type`, `timestamp`, `is_me`, `format`, `formatted_body`, `media_url`, `media_mimetype`, `reply_to_event_id` and `reactions`) and an `end` token; pass it back as `from` for older ones. On Discord a custom emoji is only in `formatted_body` (`<img data-mx-emoticon src="mxc://…" alt=":name:">`); the plain `body` drops it. `GET /media/{server_name}/{media_id}` serves the file behind `mxc://server_name/media_id` through Synapse's authenticated media API (`internal/api/media.go`), streamed, with `width`/`height` for a thumbnail.
- **Send to a person**: `POST /messages/send {user_id, body}` (`internal/api/messages.go`). It asks Matrix for the direct-message room already shared with that bridge puppet and **creates one only if none exists**, then returns `room_id`, `event_id` and `created_room`. A missing `user_id` or `body` is a 400 naming the field, a Matrix failure is a 502, and an unconfigured Matrix client is a 503.
- **Send to a group or channel** (a Discord or Slack channel, a WhatsApp group): `POST /conversations/{room_id}/send {body}`. The bridge posts it on the platform as the logged-in account — on Discord that is `@kuxr`, visible to the whole server.
- **React to a message**: `POST /conversations/{room_id}/reactions {event_id, key}` posts a reaction as our Matrix account, which the bridge relays as the logged-in account; `DELETE /conversations/{room_id}/reactions/{reaction_event_id}` takes back one we posted. A reaction made in the platform's own app belongs to our puppet and cannot be taken back from here. On Discord `key` may be `discord-emoji:<id>` for any emoji in the custom emoji catalog: multichat teaches the bridge the emoji first if it has not seen it, then reacts with its `mxc://` URI and answers that key. Our own Matrix account's reactions are logged in `reaction_log` beside the puppets' (with `platform` ""), and each reaction group says `reacted_by_me` and `my_reaction_event_id`.
- **Custom emoji**: `GET /emoji` lists every bridged Discord server's custom emoji (with `bridge_mxc` when the bridge knows it), the operator's favourites and emoji settings; `POST /emoji/discord/refresh` fetches the emoji from Discord with the Event-Manager bot's token (auth-store credential `DISCORD_EMOJI_BOT_CREDENTIAL_ID`; the bot must be in every bridged server), and scheduler job `multichat emoji refresh` runs it daily; `PUT /emoji/favorites` and `PUT /emoji/settings` store the rest. ⚠️ **Reacting with an emoji the bridge has not seen writes a row into the bridge's own `discord_file` table** (`internal/discordemoji`), the one write multichat makes into a bridge database, because mautrix-discord relays an `mxc://` reaction only for an emoji listed there. The bridge cannot send a custom emoji inside a message (it escapes `<` and drops `<img>`), so custom emoji work in reactions only. Details in `docs/api.md` under *Emoji*.
- ⚠️ `POST /conversations/new` calls `CreateDM` unconditionally, so it opens a **fresh room on every call** — it is for starting a conversation, never for sending.

Two wrappers sit on these routes. `~/bin/multichat-send` (`cmd/multichat-send`) resolves a display name plus `-platform` to a puppet id and treats an ambiguous name as an error rather than guessing. `~/bin/multichat-mcp` (`cmd/multichat-mcp`) is a stdio MCP server on the official `modelcontextprotocol/go-sdk` offering `list_contacts`, `list_conversations`, `read_messages` and `send_message` (by `user_id` for a person or `room_id` for a group).

## The platform vocabulary

`matrix.KnownPlatforms` in `internal/matrix/platform.go` is the single list of platforms — `whatsapp`, `telegram`, `signal`, `meta`, `discord`, `slack`, in the order the bridges were added — and `GET /api/inbound-platforms` serves it, so **nothing builds a platform filter from observed values**. `PlatformOfUserID` decides a platform from the puppet prefix a bridge stamps on its ghosts (`@whatsapp_…`, `@discord_…`) and returns `""` for anything that is not a bridge puppet: the bridge bots themselves, `@admin`, and any plain Matrix user. The contact, member and conversation code in `internal/matrix/client.go` all ask it. Adding a bridge means adding it to that slice and, if it can post as us, teaching `cmd/server/main.go` our own puppet id: `SelfUserIDs` holds them so the sync worker never hands our own messages to a rule. Telegram, Meta and Discord are read from the bridge databases (`TELEGRAM_DB`, `META_DB`, `DISCORD_DB`); WhatsApp and Signal are the phone number. **Slack has none yet** — once a Slack login exists, add its id or our own Slack messages will look like someone else's.

## Inbound: the sync worker and the dispatcher

With `NATS_URL` set the server runs two loops (`internal/inbound/`). **SyncWorker** long-polls Synapse `/sync` on a 30-second timeout, keeps the resume token in `matrix_sync_state`, and publishes every message a person sent as `messages.MessagingInbound` on `messaging.inbound` (JetStream, stream `MESSAGING`), dropping our own sends and our own platform puppets so no consumer ever sees itself. **It also accepts every room invite a bridge sends to `@admin`** (`internal/inbound/invites.go`): a bridge creates a room per chat and only invites us, and a room we have not joined is missing from `GET /conversations`, the log and the bus — 59 rooms, among them the WhatsApp group TBOR Thriller Flash Mob, sat invited and unseen until 2026-09-29. At startup it lists pending invites with a full `/sync`, since an incremental sync reports an invite only once; after each sync it accepts the new ones. An invite from a bridge bot or puppet is accepted, one from a plain Matrix user is logged and left. Synapse's join rate limit (429) is waited out; any other join failure is logged and the next startup retries it. The history a newly joined room arrives with is logged (the gap fill reaches back to `message_log_started_at`) but not published, so no rule fires on old messages; a failed publish stops the token advancing, so the batch is re-read. **Dispatcher** is a durable consumer of that subject named `multichat-inbound-dispatcher` (`inbound.DurableConsumerName`); it applies the `inbound_rules` table and, per match, publishes `messages.BridgeInbound` on `bridge.inbound` to start an autonomous session — the same path scheduler agent jobs take. They are joined by the bus rather than a function call so another service can consume the same subject under its own durable name and a dispatch survives a restart. `inbound_dispatches` is the audit, `UNIQUE (rule_id, event_id)` because JetStream is at-least-once. **Before it publishes, the worker writes the batch to the message log** (`internal/inbound/message_log.go`, table `message_log` in `internal/db/message_log.go`): every message a bridge puppet sent, our own puppet included, with its text, formatting (`format`, `formatted_body`), media (`media_url`, `media_mimetype`), `reply_to_event_id`, its content JSON and the room's `m.bridge` state (on Discord the server and channel ids and names). Each row has its own `id`; a live row (`source` `matrix`) carries its unique Matrix `event_id`. A sticker (`m.sticker`, how mautrix-discord sends a Discord sticker) is logged as a message with `message_type` `m.sticker`, `body` the sticker's name and its `url` and `info.mimetype` as `media_url` and `media_mimetype`; Discord's own Lottie stickers arrive with no `url` and mimetype `application/json`, so only the name can be shown. Reactions (`m.reaction`) from bridge puppets go to `reaction_log` (`internal/db/reaction_log.go`, keyed by the reaction's event id, with the target message, `reaction_key` — a unicode emoji or an `mxc://` custom emoji — and `com.beeper.reaction.shortcode`); only `m.room.message` events are published to the bus — never a reaction or a sticker, which carry no text a rule could match. Reactions made before the worker asked for them (2026-09-28, 17:15–17:56 UTC) were added by `cmd/multichat-backfill-reactions`, which pages every joined room back to `message_log_started_at` and logs reactions and redactions through the worker's own `logEvent`; running it again changes nothing. The older `messages` and `message_reactions` tables belong to an earlier design and are unused — leave them. A log made before 2026-09-28's row ids is migrated on start by `internal/db/message_log_migration.go` in one transaction. A redaction — how a bridge relays a delete, and how a reaction is removed — marks whichever it hits, message or reaction, sets `redacted_at` and keeps the text, which is the point: Synapse strips a redacted event's content, so the log is the only copy left. An edit is its own row with `replaces_event_id`. The log starts at `message_log_started_at` in `matrix_sync_state`; a sync that reports a truncated timeline makes the worker page backward from `prev_batch` to the last logged event (never past that start) before it goes on, so a restart loses nothing. A message deleted within the moment before the worker reads it arrives already redacted and is logged with no text. `redacted_by_user_id` is whoever sent the redaction — on Discord the bridge, not the person who deleted. A failed write stops the token advancing, like a failed publish. `GET /message-log` reads it (`platform`, `network_id`, `room_id`, `sender_user_id`, `q`, `deleted=true`, `include_edits=true`, `before`, `limit` ≤ 1000) and returns `messages`, newest first and edits left out unless asked for, `edits` keyed by the message they edit, and `reactions` keyed by event id or `discord:<discord_message_id>`. **The log also holds Discord history from before it began**: `cmd/multichat-import-discord-archive` adds a JSONL history fetch (raw Discord message objects) as rows with `source` `discord-archive`, no `event_id`, a unique `discord_message_id`, `format` `discord-markdown` and the Discord object as `content_json`, whose `reactions` array the API turns into reaction groups at read time. It takes only messages sent before `message_log_started_at` and looks the room, server and channel up in `DISCORD_DB` by channel id; a second run inserts nothing. On 2026-09-28 it loaded the week to that day of `#general-chat` from `~/discord-archive/reno-20s-30s/`. `GET /discord/status` (`internal/discordbridge`, `internal/api/discord_status.go`) reports the Discord side without calling Discord: it reads `DISCORD_DB` read-only — the bridge account and whether it is logged in (a SQL `discord_token IS NOT NULL`; the token's value is never read), each bridged server (`guild.bridging_mode` ≠ 0) with its text and announcement channels, their Matrix rooms and the bridge's newest `message.timestamp` — then marks the rooms `@admin` has joined from Synapse's `joined_rooms` and adds each channel's logged and deleted counts from `message_log` (edits excluded, archive rows included — what the Messages page lists), joined on the Discord channel id. `DISCORD_DB` unset is a 503 naming it, never an empty success. `NATS_URL` requires both a configured Matrix client and `LLM_BRIDGE_URL`; the server refuses to start with one and not the other. The path is proven end to end with a plain Matrix test user (`@multichat-test:chat.kayushkin.com`, still present and harmless) but **not yet with a message from a real bridged platform** — `prediction_000114` holds that at 85% and is still open.

## Inbound rules and what a write refuses

A rule is `(platform, sender_user_id, body_pattern, direct_messages_only) → start a session on instance_id with prompt_template`; an empty platform, sender or pattern means any. Every field is checked on write (`internal/api/inbound_rules.go`): a missing `name` or `prompt_template` is a 400; `platform` must be one of `matrix.KnownPlatforms`; `sender_user_id` must be a Matrix user id (`@platform_id:server`); `body_pattern` must compile as RE2; and `instance_id` is checked with llm-bridge-server, which owns instance ids — **400 when it says the id is unknown, 502 when it cannot answer, and nothing is stored either way**. The template check is the subtle one: `inbound.CheckPromptTemplate` both parses the template and **renders it against an empty `PromptFields`**, because parsing alone cannot know the field set — so `{{.NoSuchField}}` is a 400 at write time instead of a rule that fails the moment a real person writes in. `ParsePromptTemplate` with `missingkey=error` is the one parser, shared by the API and the dispatcher, so a template the API accepted is one the dispatcher can render. `GET /api/inbound-prompt-fields` serves the field list by reflection over `inbound.PromptFields`, so an editor never hardcodes it. **Zero rules means nothing happens.**

# Access and operations

## Authentication fails open

🔴 `internal/api/router.go` reads `if authToken != "" { …check the bearer token… }`, so an **empty or absent `MULTICHAT_TOKEN` does not lock everyone out — it turns authentication off entirely**. The API serves contacts, conversations and message history plus AI routes that spend the OpenAI key, so losing that one variable opens all of it — to every local process, and through dash's proxy to anyone past dash's login. With the token set, every path except `/auth/login` and `/health` needs `Authorization: Bearer <token>` or a `multichat_token` cookie and answers 401 otherwise. `deploy.sh` will not install a unit whose `MULTICHAT_TOKEN` it cannot prove is present and non-empty, and after every deploy it asserts that an unauthenticated `/api/tags` returns 401, rolling back if it does not — it checks the refusal rather than trusting the config.

## Unit, environment and secrets

The unit template is tracked at `deploy/multichat-server.service` and installed to `~/.config/systemd/user/`. It sets `PORT=8402`, `SYNAPSE_URL=http://localhost:8008`, `TELEGRAM_DB`, `META_DB`, `DISCORD_DB`, `AUTH_STORE_URL`, `DISCORD_EMOJI_BOT_CREDENTIAL_ID`, `NATS_URL` and `LLM_BRIDGE_URL`, and pins `MULTICHAT_DB` to an absolute path. **The secrets — `MULTICHAT_TOKEN`, `MATRIX_TOKEN`, `OPENAI_API_KEY`, and `AUTH_STORE_TOKEN` for the emoji refresh — live in `~/.config/multichat/multichat.env` (mode 600) and never in the tracked template**, which would publish a live Matrix token and a live OpenAI key to a public repo; `deploy.sh` refuses to deploy when that file is missing. The drop-in `multichat-server.service.d/principal-gating.conf` adds `~/.config/principal-gating-tokens.env`. No nginx site points at it any more; the Go router is rooted at `/` and `cmd/server/main.go` mounts it under `/api/` with `http.StripPrefix`.

## The Matrix stack: Synapse and the bridges

Synapse and the bridges run from `~/multichat/docker-compose.yaml` — **outside this repo and not in git**. Containers: `synapse` (published on `127.0.0.1:8008`, SQLite in the `multichat_synapse_data` volume) and `mautrix-whatsapp`, `-telegram`, `-signal`, `-meta`, `-discord`, `-slack`, on the `matrix_net` network with no host ports. Each bridge keeps its `config.yaml`, SQLite database and `registration.yaml` in `~/multichat/<bridge>-data/`, owned by root; read them with `sudo -n`. **Except Discord**: since 2026-09-29 `mautrix-discord` runs with `UID=1000`/`GID=1000`, and its image chowns `discord-data/` to that on every start, so multichat (running as that user) can add emoji rows to its database. Setting it back to 0 breaks custom emoji reactions, and `deploy.sh` refuses to deploy until it is writable again.

- **Registering a bridge with Synapse**: the registration files Synapse reads live inside its volume at `/data/<bridge>-registration.yaml` (copy one in with `docker exec -i synapse sh -c 'cat > /data/…'`), and `~/multichat/synapse/homeserver.yaml` lists them under `app_service_config_files`. Restart `synapse` after adding one.
- **A new mautrix bridge**: run its image once with `-v ~/multichat/<bridge>-data:/data` to write a default config. Set `homeserver.address: http://synapse:8008`, `homeserver.domain: chat.kayushkin.com`, `appservice.address: http://mautrix-<bridge>:<port>`, `appservice.hostname: 0.0.0.0`, a `sqlite3-fk-wal` database under `/data`, and `bridge.permissions` to only `"@admin:chat.kayushkin.com": admin`. The container's own `yq` edits it: `docker run --rm --entrypoint yq -v …:/data <image> -I4 e -i '…' /data/config.yaml`. Run it once more to write `registration.yaml`.
- **Upgrading**: `docker compose pull` then `docker compose up -d` in `~/multichat`. Back up first — Synapse and the bridges migrate their databases forward and cannot go back. The 2026-09-28 upgrade (Synapse 1.150 → 1.161) left its backup in `~/backups/matrix-2026-09-28/`.
- ⚠️ **Telegram is pinned** to `mautrix-telegram-python:pinned-2026-02-11`, a local tag of the last Python release. `dock.mau.dev/mautrix/telegram:latest` is now a Go rewrite with a different config and database, so moving to it is a migration, not a pull.
- **Instagram is gone**: the current mautrix-meta refuses Instagram logins (`meta-ig-not-supported`); only Facebook Messenger remains.
- **Discord servers are opt-in**: a login bridges DMs only. `guilds status` in the Discord bot's room lists every server with its id, and `guilds bridge <id> --entire` creates a Matrix room per channel. `@admin` is only *invited*; the sync worker accepts it (below).

## Logging a bridge in

Every bridge is logged in as `@admin`, whose token is `MATRIX_TOKEN` in `~/.config/multichat/multichat.env`. You talk to a bridge by sending text to its bot (`@whatsappbot`, `@signalbot`, `@metabot`, `@telegrambot`, `@discordbot`, `@slackbot`, all `:chat.kayushkin.com`) in a two-person room with `@admin`. Each bridge posts its connection state there too, so that room is where to look first when a platform goes quiet — bridges log out without anything else noticing. On 2026-09-28 every one of the original four was found logged out, WhatsApp since 2026-09-07.

- A room the bot does not treat as its management room needs the command prefix (`!wa login`, and `!wa <answer>` for each reply); the bot says so when it happens. A fresh direct-message room with just the bot becomes its management room and needs no prefix.
- `login` on the mautrix-go bridges lists the flows. **WhatsApp**: `login phone`, then the number in international form, returns an 8-character pairing code the user types into WhatsApp (Linked devices → Link with phone number instead). **Signal**: `login` returns a QR code for Signal's Linked devices. **Meta**: `login messenger` (cookies from messenger.com) or `login messenger-lite` (username and password). **Slack**: `login email`, `login token` (token plus `d` cookie from a browser) or `login app`. **Discord**: `login-qr`, scanned from the Discord app's own Scan QR Code screen, not the phone camera; `login-token user <token>` is the fallback. **Telegram** (the pinned Python bridge): `login`, then the phone number, then the code Telegram sends to the user's app.
- ⚠️ **QR codes die in 45–60 seconds** — Signal makes a new one every 45 seconds as an edit of the same message, and Discord closes its login socket after 60. A code relayed through chat is dead on arrival: Signal says "network failed", Discord says "can't find that device". Show the live code on a page the user opens on a *second* screen (they cannot scan their own phone's screen), refreshed every few seconds, and restart the login on demand. Pairing codes and phone-number logins last a few minutes; start one only when the user is ready.
- `cancel` stops a pending login. `logout`, `list-logins` and `help` are on every mautrix-go bridge.

## How other services reach it

**dash** proxies a deliberate subset at `/api/multichat/*` (`dash/server/api_multichat.go`, `multichatProxiedRoutes`) for bridge-ui's Inbound rules, Messages and Discord pages: the inbound-rule routes, `GET /contacts/unified`, `GET /conversations`, `GET /conversations/{room_id}/messages`, `POST /conversations/{room_id}/send`, `GET /search`, the reaction routes, the tag routes, `GET /message-log`, `GET /discord/status`, media, and the emoji routes (`GET /emoji`, `POST /emoji/discord/refresh`, `PUT /emoji/favorites`, `PUT /emoji/settings`). **Since 2026-09-28 dash is multichat's web front end and a dash login can send into a conversation**; `POST /conversations/new`, `POST /messages/send`, uploads and the AI routes stay refused, and anything not listed is a 404 decided **before** a token is asked for. The token is resolved from auth-store provider `multichat` on each request, so a rotation needs no restart. **`~/bin/multichat-send`** resolves the same token from that provider using `AUTH_STORE_URL` and `AUTH_STORE_TOKEN`, which the scheduler unit gets from the drop-in `scheduler.service.d/multichat-send.conf`; disabled scheduler job 86 `multichat-send example` is the template to copy. **`~/bin/multichat-mcp`** is registered in tool-store as `multichat` (id 15), provisioned with a token from auth-store and opted in per instance on the bridge Tools page; permission-store rule `multichat-send-message-ask` makes `mcp__multichat__send_message` `ask` at global scope, so a human confirms each send. ⚠️ **That holds only in a session whose tool calls reach permission-store**: llm-bridge-server allows a session in `bypass` permission mode before any rule is read (noteboard todo `bfd3f4de-af8e-4e7e-8e52-0671a22cdf81`), so for an unattended session the real guard is that its instance has not opted in to this tool. **kanban-store's** message triggers send through `POST /api/messages/send` — see its row for why delivery is off by default.

# Working in this repo

## Build, test and deploy

Module `github.com/kayushkin/multichat`, with `replace` directives on `../bus` and `../llm-bridge`, so both sibling clones must be present to build. Five binaries: `cmd/server` (the service, installed as `~/bin/multichat-server`), `cmd/multichat-send`, `cmd/multichat-mcp`, and two one-offs: `cmd/multichat-import-discord-archive` (flags only) and `cmd/multichat-backfill-reactions` (`-db`, plus `SYNAPSE_URL` and `MATRIX_TOKEN`). `go build ./...` and `go test ./...` need no build tag. Deploy with `./deploy.sh`, which builds the binaries, checks the secrets, restarts the unit and asserts the 401 before reporting success. Pushes to `github.com/kayushkin/multichat`. **Every environment variable is declared in `internal/config`** (llm-bridge `servicesettings`): the server's sixteen in `settings.go`, served at `GET /api/settings` behind the bearer, and the commands' own in `commands.go`. Nothing calls `os.Getenv`; a source-scan test fails on an undeclared read and holds each client to its own list. The server owns full names, never `MULTICHAT_` (`MULTICHAT_URL` is how other services find it), so `MULTICHAT_DB_PATH` stops the start and `MULTICHAT_URL` does not. `NATS_URL` without the Matrix client or `LLM_BRIDGE_URL` is refused in `config.Load`, and `deploy.sh` runs `TestTheLiveProcessEnvironmentBuildsARegistry` against the running unit's `/proc/<pid>/environ` before it installs anything.

## The database is pinned absolutely

SQLite at `~/repos/multichat/multichat.db`, pinned by `MULTICHAT_DB`. **SQLite does not fail on a missing file, it creates one**, so when `cmd/server/main.go` opened the bare relative path the database was wherever systemd happened to chdir: get the working directory wrong and multichat comes up with every route answering out of a brand-new empty database, looking perfectly healthy while the real contacts and tags sit untouched on disk. The absolute path removes the ambiguity, and `deploy.sh` refuses to deploy when the file named there does not already exist. The inbound schema (`internal/db/inbound.go`) adds `matrix_sync_state`, `inbound_rules` and `inbound_dispatches` to the older tables in `internal/db/db.go`.

## Generated TypeScript types

`./generate-ts.sh` runs tygo per `tygo.yaml` and renders `internal/db/inbound.go`, `internal/db/message_log.go` (`LoggedMessage`, `MessageReactionGroup`, `MessageLogPage`) and `internal/db/emoji.go` (`EmojiCatalog`, `DiscordCustomEmoji`, `EmojiSettings`) to `ts/db.ts` and `internal/discordbridge/status.go` to `ts/discord_status.ts`; the hand-written `ts/index.ts` only re-exports them, and the whole is published source-only as `@kayushkin/multichat-types`. Each output file gets a header naming the commit it was generated from. The Go structs are the source of truth — regenerate after changing a wire type rather than editing the render. tygo keeps one entry per Go package and renders every exported type in an included file, so a type that is not on the wire (`MessageLogFilter`, `ChannelLogCounts`, `LoggedReaction`) lives in a file that is not included (`message_log_queries.go`, `reaction_log.go`). **Only what another UI reads is rendered** — bridge-ui's Inbound rules, Discord and Emoji pages and its emoji pickers — and bridge-ui's Messages pages keep hand-written types for the conversation routes, which are not rendered yet.
