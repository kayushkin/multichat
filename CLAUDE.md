# About multichat

## What it owns

`127.0.0.1:8402` (`PORT`, and `MULTICHAT_LISTEN_HOST`, loopback by default), unit `multichat-server.service`. The unified inbox over a Synapse Matrix homeserver (`127.0.0.1:8008`) with seven **mautrix** bridges in Docker — **whatsapp, telegram, signal, meta** (Facebook Messenger; the current bridge no longer carries Instagram), **discord**, **slack** and **gmessages** (the operator's SMS, MMS and RCS texts, through Google Messages on their phone). The Go API only ever talks to Synapse's client API and speaks no platform protocol of its own. **This is the way agents read and message people on Discord**; `si` still carries its own older Discord feed for inber, and matterbridge is not involved. **Its web UI is dash**: bridge-ui's Messages pages (Conversations, Search, Contacts, Discord) reach this API through dash's proxy. The old site at `chat.kayushkin.com` — a React app under `frontend/` plus `/api` and `/ws` on the internet — was switched off on 2026-09-28; its code is in git history, and `deploy.sh` removes its nginx site wherever it is still installed. `docs/api.md` is the route table; `docs/llm-bridge-integration.md` records the design choice — Option D (the bus for inbound events, direct HTTP for sends, no outbound over the bus) plus Option C (the MCP tool surface for agents).

## Where this prompt lives

These sections are stored in agent-store as a project prompt collection and rendered, with identical text, to `AGENTS.md` and `CLAUDE.md` at the root of this repo, so that whichever file a harness reads it gets the same thing. Edit them on dash `/files`, or edit either rendered file: the 15-minute scan carries the edit back into the sections and out to the other file. The host prompt keeps one row for this repo with only what an agent elsewhere needs.

# How it works

## Reading and sending messages

Every route below is under `localhost:8402/api` (and, for the subset dash forwards, `dash.kayushkin.com/api/multichat`) and needs `Authorization: Bearer $MULTICHAT_TOKEN`.

- **Find a conversation**: `GET /conversations` lists joined rooms with `room_id`, `name`, `platform`, member ids, the last message and, in a one-to-one DM, `direct_message_partner_user_id`, newest first. **Tags** go on people (`/contacts/tags`) or on rooms (`/conversations/tags`, `GET /conversations/tags/bulk`); a room's shown tags are its own plus, in a DM, the partner's. **Links** join rooms on different apps that are one conversation (`GET`/`POST /conversations/links`, `POST /conversations/links/remove`, tables `conversation_links` and `conversation_link_rooms`): the Conversations page lists a link as one entry with a tab per room, and the rooms themselves stay separate. **Hiding**: each room carries `visibility` (`hidden`, `shown` or `auto`) and `hidden`; `PUT /conversations/{room_id}/visibility` sets the choice and `GET`/`PUT /conversations/visibility-settings` the auto-hide rule (on, above 30 members, by default; tables `conversation_visibility` and `conversation_visibility_settings`). ⚠️ A room is listed only when a bridge puppet is a member, so a Discord or Slack channel nobody has posted in since it was bridged is missing from the list. It still works by its `room_id`, which the bridge's management room or Synapse's `joined_rooms` gives you. **The list comes from memory** (`internal/matrix/conversation_cache.go`): at startup the server reads every joined room, eight at a time (about 12 s for 380 rooms, three or four Synapse requests each), and a `/sync` loop of its own then reads again only a room that had a message, redaction, name, member or `m.bridge` event, and drops a room we left. The first request after a restart waits for that first read; a room whose read failed makes the list a 500 naming it, and every sync retries it.
- **Read**: `GET /conversations/{room_id}/messages?limit=50` returns `messages` (each `event_id`, `sender`, `sender_name`, `body`, `msg_type`, `timestamp`, `is_me`, `format`, `formatted_body`, `media_url`, `media_mimetype`, `reply_to_event_id` and `reactions`) and an `end` token; pass it back as `from` for older ones. On Discord a custom emoji is only in `formatted_body` (`<img data-mx-emoticon src="mxc://…" alt=":name:">`); the plain `body` drops it. `GET /media/{server_name}/{media_id}` serves the file behind `mxc://server_name/media_id` through Synapse's authenticated media API (`internal/api/media.go`), streamed, with `width`/`height` for a thumbnail.
- **Send to a person**: `POST /messages/send {user_id, body}` (`internal/api/messages.go`). It asks Matrix for the direct-message room already shared with that bridge puppet and **creates one only if none exists**, then returns `room_id`, `event_id` and `created_room`. A missing `user_id` or `body` is a 400 naming the field, a Matrix failure is a 502, and an unconfigured Matrix client is a 503.
- **Send a file** (an image, video or any file, with an optional caption): `POST /conversations/{room_id}/send-file`, a multipart form with `file` and `caption`, up to Synapse's upload limit (50 MB). On Discord the caption and the file arrive as one message.
- **Send to a group or channel** (a Discord or Slack channel, a WhatsApp group): `POST /conversations/{room_id}/send {body}`. The bridge posts it on the platform as the logged-in account — on Discord that is `@kuxr`, visible to the whole server.
- **React to a message**: `POST /conversations/{room_id}/reactions {event_id, key}` posts a reaction as our Matrix account, which the bridge relays as the logged-in account; `DELETE /conversations/{room_id}/reactions/{reaction_event_id}` takes back one we posted. A reaction made in the platform's own app belongs to our puppet and cannot be taken back from here. On Discord `key` may be `discord-emoji:<id>` for any emoji in the custom emoji catalog: multichat teaches the bridge the emoji first if it has not seen it, then reacts with its `mxc://` URI and answers that key. Our own Matrix account's reactions are logged in `reaction_log` beside the puppets' (with `platform` ""), and each reaction group says `reacted_by_me` and `my_reaction_event_id`.
- **Custom emoji**: `GET /emoji` lists every bridged Discord server's custom emoji (with `bridge_mxc` when the bridge knows it), the operator's favourites and emoji settings; `POST /emoji/discord/refresh` fetches the emoji from Discord with the Event-Manager bot's token (auth-store credential `DISCORD_EMOJI_BOT_CREDENTIAL_ID`; the bot must be in every bridged server), and scheduler job `multichat emoji refresh` runs it daily; `PUT /emoji/favorites` and `PUT /emoji/settings` store the rest. `GET /emoji` also lists `discord_seen_emoji` (emoji the bridge has relayed from servers that are not bridged) and the latest Nitro check: ⚠️ **`POST /emoji/discord/nitro-check` reads the Discord account's own login from the bridge's `user` table** for one `GET /users/@me`, at most once a day and only when a Messages page opens (the operator chose this on 2026-09-29); it is the one place multichat reads that login, and it never logs, stores or answers it. With Nitro a Discord room is offered every server's emoji and the seen ones. ⚠️ **The day's first Nitro check also starts a sweep that lists every other server the account is in with that same login** (`internal/discordemoji/server_sweep.go`, chosen by the operator on 2026-09-30): one call for the server list, then one server's emoji every 30 seconds, each server at most once a week. Keep that pace; Discord's own app never makes these calls. ⚠️ **Reacting with an emoji the bridge has not seen writes a row into the bridge's own `discord_file` table** (`internal/discordemoji`), the one write multichat makes into a bridge database, because mautrix-discord relays an `mxc://` reaction only for an emoji listed there. The bridge cannot send a custom emoji inside a message (it escapes `<` and drops `<img>`), so custom emoji work in reactions only. Details in `docs/api.md` under *Emoji*.
- **Awaiting reply**: `GET /awaiting-reply` lists conversations holding a message the operator has not answered from someone they tagged, **by person**: a people-store person counts when any of their accounts carries a chosen tag (`PUT /awaiting-reply/settings`), and then all their accounts count; a tagged room counts everyone. A tagged person counts only in rooms of at most `max_group_member_count` (the operator included) and never in a Discord server channel. Replying from any app clears a room through the message log; opening or dismissing it in dash posts `POST /awaiting-reply/clears`. Rules in `internal/awaitingreply` (tested in `compute_test.go`), routes in `docs/api.md` under *Awaiting reply*; bridge-ui's Waiting on you page and chat sidebar section read it.
- ⚠️ `POST /conversations/new` calls `CreateDM` unconditionally, so it opens a **fresh room on every call** — it is for starting a conversation, never for sending.

Two wrappers sit on these routes. `~/bin/multichat-send` (`cmd/multichat-send`) resolves a display name plus `-platform` to a puppet id — the person's name or that account's own name — or a people-store `-person` id plus `-platform`, and treats an ambiguous match as an error rather than guessing. `~/bin/multichat-mcp` (`cmd/multichat-mcp`) is a stdio MCP server on the official `modelcontextprotocol/go-sdk` offering `list_contacts`, `list_conversations`, `read_messages` and `send_message` (by `user_id` for a person or `room_id` for a group).

## The platform vocabulary

`matrix.KnownPlatforms` in `internal/matrix/platform.go` is the single list of platforms — `whatsapp`, `telegram`, `signal`, `meta`, `discord`, `slack`, `gmessages`, `gmessagesweb`, in the order the bridges were added — and `GET /api/inbound-platforms` serves it, so **nothing builds a platform filter from observed values**. `PlatformOfUserID` decides a platform from the puppet prefix a bridge stamps on its ghosts (`@whatsapp_…`, `@discord_…`) and returns `""` for anything that is not a bridge puppet: the bridge bots themselves, `@admin`, and any plain Matrix user. The contact, member and conversation code in `internal/matrix/client.go` all ask it. Adding a bridge means adding it to that slice and, if it can post as us, teaching `cmd/server/main.go` our own puppet id: `SelfUserIDs` holds them so the sync worker never hands our own messages to a consumer. Telegram, Meta and Discord are read from the bridge databases (`TELEGRAM_DB`, `META_DB`, `DISCORD_DB`); Signal is the phone number, and WhatsApp is both the phone number and our LID puppet (`@whatsapp_lid-…`), read from `WHATSAPP_DB`'s `whatsmeow_device` — without it every WhatsApp room counts us as a member and no WhatsApp DM names its partner. Google Messages is read from `GMESSAGES_DB`: each login's `metadata` holds `id_prefix` and `self_participant_ids`, and our puppet is `@gmessages_<id_prefix>.<participant id>` (`@gmessages_1.2` since the first pairing on 2026-10-01). **`gmessagesweb`** is repo gmessages-web-bridge, not a mautrix bridge: a Chrome extension reads Google Messages for web on the MacBook into Matrix, and our own texts from the phone come as one puppet, `@gmessagesweb_self`, hardcoded here to match that repo's `SelfPuppetLocalpart`. **Slack has none yet** — once a Slack login exists, add its id or our own Slack messages will look like someone else's.

## People: accounts linked to people-store persons

**A person is a people-store id (`person_000001`); each bridge account is a people-store identity of kind `matrix_user`, and people-store keeps who linked it and why** (`internal/people` is the client, `internal/contactlinks` the linker, routes in `docs/api.md` under *Linking identities to people*). The operator decided on 2026-10-01 that people-store owns "person"; principal-store is only who logs in, holds grants and gets cards. `GET /contacts/unified` groups by person id and reads names from people-store (`PEOPLE_STORE_URL`), so a journal entry or note can point at the same person with a `person_…` chip, and `multichat-send -person person_… -platform …` and the MCP tool's `person_id` filter join on it. **Names never join anything**: until 2026-10-01 it merged identities whose display names matched, which merged strangers who shared a first name. Three sources link, each recorded in people-store as `linked_by` with a `reason`: **`operator`** (the person picker on bridge-ui's Messages pages, through `POST /contacts/links`), **`phone_number`** (`LinkByPhoneNumber`, at start and every 10 minutes, over the four phone-based bridge databases — only multichat can read those) and **`agent`** (the review pass). people-store refuses the automatic two a handle the operator took off a person (an unlink, or a rejected suggestion, writes a refusal there) and never lets them move a handle; multichat adds that they never join two accounts that both have people. The phone matcher creates a new person only for someone we talk with (sent a logged message, or the partner in a joined one-to-one chat): WhatsApp alone holds about 2,000 puppets from group chats. **Suggestions and the review queue live in people-store**: an unsure agent writes a people-store suggestion, which the operator decides on dash's `/people` page, and the agent's queue is people-store's `GET /reviews/pending`. **Scheduler job 101 `multichat contact review trigger`** runs `scripts/contact-review-trigger.sh` every 5 minutes: when handles wait, no session holds a claim and job 100 has not started in the last 15 minutes, it runs **job 100 `multichat contact review`**, an agent job whose prompt claims 25 handles in people-store, links those it would bet 9 to 1 on through `POST /contacts/links`, suggests in people-store the ones it half-believes, and marks all 25 reviewed there. Change what the agent does by editing job 100's prompt.

⚠️ **Legacy tables, migrated 2026-10-01**: `contact_identity_links`, `contact_link_refusals`, `contact_link_suggestions`, `contact_review_claims` and `contact_reviews` in `multichat.db` held these links for a few hours on 2026-10-01, pointing at principal-store contact principals. `scripts/migrate-contact-links-to-people-store.py` copied them to people-store; nothing reads or writes them now. Leave them; do not build on them.

`ListContacts` reads every page of Synapse's user list; until 2026-10-01 it read one page of 500 and silently hid about 1,800 of 2,300 identities.

## Inbound: the sync worker

With `NATS_URL` set the server runs two loops (`internal/inbound/`): **SyncWorker**, below, and the **AutoReactor** (see *Auto-reactions*). **SyncWorker** long-polls Synapse `/sync` on a 30-second timeout, keeps the resume token in `matrix_sync_state`, and publishes every message a person sent as `messages.MessagingInbound` on `messaging.inbound` (JetStream, stream `MESSAGING`), dropping our own sends and our own platform puppets so no consumer ever sees itself. **It also accepts every room invite a bridge sends to `@admin`** (`internal/inbound/invites.go`): a bridge creates a room per chat and only invites us, and a room we have not joined is missing from `GET /conversations`, the log and the bus — 59 rooms, among them the WhatsApp group TBOR Thriller Flash Mob, sat invited and unseen until 2026-09-29. At startup it lists pending invites with a full `/sync`, since an incremental sync reports an invite only once; after each sync it accepts the new ones. An invite from a bridge bot or puppet is accepted, one from a plain Matrix user is logged and left. Synapse's join rate limit (429) is waited out; any other join failure is logged and the next startup retries it. The history a newly joined room arrives with is logged (the gap fill reaches back to `message_log_started_at`) but not published, so no consumer is handed old messages; **and it invites the Discord bridge's bot into any room the bot is missing from** (`internal/inbound/bridgebots.go`): the bot is whichever the room's `m.bridge` state names as `bridgebot`, and only bridges whose `m.bridge` protocol id is in `bridgeProtocolsThatDropOurMessagesWithoutTheirBot` (today just `discordgo`) get it. Add one only on evidence of a dropped message. The pinned Telegram bridge is left out on purpose: it needs no bot in its rooms, and invited into a room with only us, it treats that room as one for bridge commands (it did this to the operator's Saved Messages room on 2026-10-20). A bridge relays what we send from the platform's own app through our own puppet, and its bot has to invite that puppet in first; mautrix-discord creates some direct-message rooms without its bot, and there it drops our messages (`All parts of message failed to send to Matrix` in its log) — seven to one person before 2026-09-29. Every joined room is checked at startup and each newly joined room after its invite is accepted, on a goroutine of its own, since Synapse lets a user receive only a few invites in a burst and the wait must not hold up the sync. A bot already invited, or banned, is logged and left; a failed publish stops the token advancing, so the batch is re-read. **Agent sessions started by a chat message are scheduler jobs with an `event_trigger` on `messaging.inbound`**: scheduler reads the subject through its own durable consumer, `scheduler-event-triggers-messaging-inbound`, and starts an agent run per matching message with a prompt filled from it — see "Event triggers" in `~/repos/scheduler/AGENTS.md`. multichat starts no session itself. Its own inbound-rule dispatcher (tables `inbound_rules` and `inbound_dispatches`, durable `multichat-inbound-dispatcher`) did that job from 2026-09-11 until 2026-10-28, when scheduler's triggers replaced it; `internal/db/sync_state.go` drops both tables on start. The worker and its consumers are joined by the bus rather than a function call so any service can consume the subject under its own durable name and a message survives a restart. **Before it publishes, the worker writes the batch to the message log** (`internal/inbound/message_log.go`, table `message_log` in `internal/db/message_log.go`): every message a bridge puppet sent, our own puppet included, with its text, formatting (`format`, `formatted_body`), media (`media_url`, `media_mimetype`), `reply_to_event_id`, its content JSON and the room's `m.bridge` state (on Discord the server and channel ids and names). Each row has its own `id`; a live row (`source` `matrix`) carries its unique Matrix `event_id`. A sticker (`m.sticker`, how mautrix-discord sends a Discord sticker) is logged as a message with `message_type` `m.sticker`, `body` the sticker's name and its `url` and `info.mimetype` as `media_url` and `media_mimetype`; Discord's own Lottie stickers arrive with no `url` and mimetype `application/json`, so only the name can be shown. Reactions (`m.reaction`) from bridge puppets go to `reaction_log` (`internal/db/reaction_log.go`, keyed by the reaction's event id, with the target message, `reaction_key` — a unicode emoji or an `mxc://` custom emoji — and `com.beeper.reaction.shortcode`); only `m.room.message` events are published to the bus — never a reaction or a sticker, which carry no text a consumer could match. Reactions made before the worker asked for them (2026-09-28, 17:15–17:56 UTC) were added by `cmd/multichat-backfill-reactions`, which pages every joined room back to `message_log_started_at` and logs reactions and redactions through the worker's own `logEvent`; running it again changes nothing. The older `messages` and `message_reactions` tables belong to an earlier design and are unused — leave them. A log made before 2026-09-28's row ids is migrated on start by `internal/db/message_log_migration.go` in one transaction. A redaction — how a bridge relays a delete, and how a reaction is removed — marks whichever it hits, message or reaction, sets `redacted_at` and keeps the text, which is the point: Synapse strips a redacted event's content, so the log is the only copy left. An edit is its own row with `replaces_event_id`. The log starts at `message_log_started_at` in `matrix_sync_state`; a sync that reports a truncated timeline makes the worker page backward from `prev_batch` to the last logged event (never past that start) before it goes on, so a restart loses nothing. A message deleted within the moment before the worker reads it arrives already redacted and is logged with no text. `redacted_by_user_id` is whoever sent the redaction — on Discord the bridge, not the person who deleted. A failed write stops the token advancing, like a failed publish. `GET /message-log` reads it (`platform`, `network_id`, `room_id`, `sender_user_id`, `q`, `deleted=true`, `include_edits=true`, `before`, `limit` ≤ 1000) and returns `messages`, each with a `ref` (`message_026563`, the row id) that `GET /message-log/{ref}` answers and kanban-store's entity type `message` makes a chip — so a timeline cites a message by its ref, and `cmd/multichat-backfill-room -db … -room '!…'` first logs a room's whole Synapse history, past `message_log_started_at`, when the message to cite is older than the log; newest first and edits left out unless asked for, `edits` keyed by the message they edit, and `reactions` keyed by event id or `discord:<discord_message_id>`. **The log also holds Discord history from before it began**: `cmd/multichat-import-discord-archive` adds a JSONL history fetch (raw Discord message objects) as rows with `source` `discord-archive`, no `event_id`, a unique `discord_message_id`, `format` `discord-markdown` and the Discord object as `content_json`, whose `reactions` array the API turns into reaction groups at read time. It keeps a message only if it was sent before the first message the live sync logged in that room (so a server bridged later keeps the weeks between), looks the room, server and channel up in `DISCORD_DB` by channel id, and a second run inserts nothing. **`cmd/multichat-fetch-discord-history -discord-db … -server <id> -out <dir> [-images] [-pause 3s]`** writes that JSONL: it reads a bridged server's text channels' history through the bridge's logged-in account (the login read as the Nitro check reads it, held in memory, sent only to discord.com), one request at a time with a pause before each (at least a second, 3 s by default), waiting out every 429 for as long as Discord asks and stopping after 10 in a row; `<channel>.done` marks a finished channel so a rerun skips it, and `-images` saves each image attachment (no login sent to the CDN) with `images.jsonl` naming its message. `-direct-message <channel id>` (repeatable, no `-server` needed) fetches a DM or group DM the account is in, bridged or not, into `<out>/direct-messages/`; on 2026-10-26 it fetched 24 of the user's DMs for journal-store's Discord transcripts. On 2026-10-23 it fetched the user's own servers Pretend, Riverside House and wareboxes into `~/.local/share/life-archive/discord/`. On 2026-09-28 it loaded the week to that day of `#general-chat` from `~/discord-archive/reno-20s-30s/`. `GET /discord/status` (`internal/discordbridge`, `internal/api/discord_status.go`) reports the Discord side without calling Discord: it reads `DISCORD_DB` read-only — the bridge account and whether it is logged in (a SQL `discord_token IS NOT NULL`; the token's value is never read), each bridged server (`guild.bridging_mode` ≠ 0) with its text and announcement channels, their Matrix rooms and the bridge's newest `message.timestamp` — then marks the rooms `@admin` has joined from Synapse's `joined_rooms` and adds each channel's logged and deleted counts from `message_log` (edits excluded, archive rows included — what the Messages page lists), joined on the Discord channel id. `DISCORD_DB` unset is a 503 naming it, never an empty success. `NATS_URL` requires a configured Matrix client; the server refuses to start with `NATS_URL` set and no Matrix client. `LLM_BRIDGE_URL` no longer has anything to do with inbound: only the short-name pass uses it. `prediction_000114` (whether the inbound path works with a message from a real bridged platform) was about the old dispatcher, not scheduler's triggers. The plain Matrix test user `@multichat-test:chat.kayushkin.com` that proved the dispatcher end to end is still present and harmless.

## Auto-reactions

A rule is `(sender_user_id, room_id, reaction_key)`: our own account reacts with `reaction_key` to every message that sender writes in `room_id`, or in every room when `room_id` is `""` (table `auto_reactions`, `internal/db/auto_reactions.go`). The reaction goes out as our Matrix account, which the bridge relays as the operator's own account, so on Discord or Google Messages people see the operator react. **`AutoReactor`** (`internal/inbound/auto_reactor.go`) is a durable consumer of `messaging.inbound`, named `multichat-auto-reactor`, beside scheduler's, so it sees only what the sync worker publishes: messages people sent after we joined, never stickers, and never our own. ⚠️ **A rule reacts only to messages sent after its `created_at`**: a new durable starts by replaying the whole `MESSAGING` stream, which would otherwise put reactions on weeks of old messages. `auto_reaction_claims` (`PRIMARY KEY (rule_id, event_id)`) stops a redelivery reacting twice. Each rule keeps `reaction_count`, `last_reacted_at` and its last refusal in `last_error`. **A platform's refusal reaches the rule too**: Matrix accepting a reaction says nothing about the platform, and from 2026-10-02 16:33 UTC Discord refused every 🥛 on Lukas in the Riverside server (`403`, code `90001`, "Reaction blocked") while the rule counted 300 of them as made. So each claim keeps the reaction event it sent (`auto_reaction_claims.reaction_event_id`); mautrix-discord, with `message_status_events: true` in `~/multichat/discord-data/config.yaml` (set 2026-10-20), answers every event we send with a `com.beeper.message_send_status`; the sync worker asks for those events and, on a `FAIL_…` status that names an auto-reaction's event, stores the refusal on the claim (`platform_error`), takes one off the rule's count and puts the refusal in `last_error` (`db.RecordAutoReactionPlatformFailure`). Other bridges send no status events unless their config turns them on, so there a refusal still goes unseen. Routes: `GET`/`POST /auto-reactions`, `PATCH`/`DELETE /auto-reactions/{id}`; `GET` fills `sender_display_name` and `room_name` from Matrix for display, never stored. `reaction_key` is a unicode emoji or an `mxc://` URI; a catalog key (`discord-emoji:…`) is a 400 until the auto-reactor learns to teach the bridge first, as `POST /conversations/{room_id}/reactions` does. bridge-ui shows them on Messages → Auto-reactions, beside the Event-Manager bot's own rules from discord-signup-store. The first rules (2026-10-02) put 🥛 on Lukas: on Discord in every room, and in the Google Messages group with Leah and Priya.

# Access and operations

## Authentication fails open

🔴 `internal/api/router.go` reads `if authToken != "" { …check the bearer token… }`, so an **empty or absent `MULTICHAT_TOKEN` does not lock everyone out — it turns authentication off entirely**. The API serves contacts, conversations and message history plus AI routes that spend the OpenAI key, so losing that one variable opens all of it — to every local process, and through dash's proxy to anyone past dash's login. With the token set, every path except `/auth/login` and `/health` needs `Authorization: Bearer <token>` or a `multichat_token` cookie and answers 401 otherwise. `deploy.sh` will not install a unit whose `MULTICHAT_TOKEN` it cannot prove is present and non-empty, and after every deploy it asserts that an unauthenticated `/api/tags` returns 401, rolling back if it does not — it checks the refusal rather than trusting the config.

## Unit, environment and secrets

The unit template is tracked at `deploy/multichat-server.service` and installed to `~/.config/systemd/user/`. It sets `PORT=8402`, `SYNAPSE_URL=http://localhost:8008`, `TELEGRAM_DB`, `META_DB`, `DISCORD_DB`, `WHATSAPP_DB`, `GMESSAGES_DB`, `SIGNAL_DB`, `PEOPLE_STORE_URL`, `SHORT_NAME_STORE_URL`, `AUTH_STORE_URL`, `DISCORD_EMOJI_BOT_CREDENTIAL_ID`, `NATS_URL` and `LLM_BRIDGE_URL`, and pins `MULTICHAT_DB` to an absolute path. **The secrets — `MULTICHAT_TOKEN`, `MATRIX_TOKEN`, `OPENAI_API_KEY`, and `AUTH_STORE_TOKEN` for the emoji refresh — live in `~/.config/multichat/multichat.env` (mode 600) and never in the tracked template**, which would publish a live Matrix token and a live OpenAI key to a public repo; `deploy.sh` refuses to deploy when that file is missing. The drop-in `multichat-server.service.d/principal-gating.conf` adds `~/.config/principal-gating-tokens.env`. No nginx site points at it any more; the Go router is rooted at `/` and `cmd/server/main.go` mounts it under `/api/` with `http.StripPrefix`.

## The Matrix stack: Synapse and the bridges

Synapse and the bridges run from `~/multichat/docker-compose.yaml` — **outside this repo and not in git**. Containers: `synapse` (published on `127.0.0.1:8008`, SQLite in the `multichat_synapse_data` volume) and `mautrix-whatsapp`, `-telegram`, `-signal`, `-meta`, `-discord`, `-slack`, `-gmessages`, on the `matrix_net` network with no host ports. Each bridge keeps its `config.yaml`, SQLite database and `registration.yaml` in `~/multichat/<bridge>-data/`, owned by root; read them with `sudo -n`. **Except Discord**: since 2026-09-29 `mautrix-discord` runs with `UID=1000`/`GID=1000`, and its image chowns `discord-data/` to that on every start, so multichat (running as that user) can add emoji rows to its database. Setting it back to 0 breaks custom emoji reactions, and `deploy.sh` refuses to deploy until it is writable again.

- **Registering a bridge with Synapse**: the registration files Synapse reads live inside its volume at `/data/<bridge>-registration.yaml` (copy one in with `docker exec -i synapse sh -c 'cat > /data/…'`), and `~/multichat/synapse/homeserver.yaml` lists them under `app_service_config_files`. Restart `synapse` after adding one.
- **A new mautrix bridge**: run its image once with `-v ~/multichat/<bridge>-data:/data` to write a default config. Set `homeserver.address: http://synapse:8008`, `homeserver.domain: chat.kayushkin.com`, `appservice.address: http://mautrix-<bridge>:<port>`, `appservice.hostname: 0.0.0.0`, a `sqlite3-fk-wal` database under `/data`, and `bridge.permissions` to only `"@admin:chat.kayushkin.com": admin`. The container's own `yq` edits it: `docker run --rm --entrypoint yq -v …:/data <image> -I4 e -i '…' /data/config.yaml`. Run it once more to write `registration.yaml`.
- **Upgrading**: `docker compose pull` then `docker compose up -d` in `~/multichat`. Back up first — Synapse and the bridges migrate their databases forward and cannot go back. The 2026-09-28 upgrade (Synapse 1.150 → 1.161) left its backup in `~/backups/matrix-2026-09-28/`.
- ⚠️ **Telegram is pinned** to `mautrix-telegram-python:pinned-2026-02-11`, a local tag of the last Python release. `dock.mau.dev/mautrix/telegram:latest` is now a Go rewrite with a different config and database, so moving to it is a migration, not a pull.
- **Instagram is gone**: the current mautrix-meta refuses Instagram logins (`meta-ig-not-supported`); only Facebook Messenger remains.
- **Discord servers are opt-in**: a login bridges DMs only. `guilds status` in the Discord bot's room lists every server with its id, and `guilds bridge <id> --entire` creates a Matrix room per channel. `@admin` is only *invited*; the sync worker accepts it (below).

## Logging a bridge in

Every bridge is logged in as `@admin`, whose token is `MATRIX_TOKEN` in `~/.config/multichat/multichat.env`. You talk to a bridge by sending text to its bot (`@whatsappbot`, `@signalbot`, `@metabot`, `@telegrambot`, `@discordbot`, `@slackbot`, `@gmessagesbot`, all `:chat.kayushkin.com`) in a two-person room with `@admin`. Each bridge posts its connection state there too, so that room is where to look first when a platform goes quiet — bridges log out without anything else noticing. On 2026-09-28 every one of the original four was found logged out, WhatsApp since 2026-09-07.

- A room the bot does not treat as its management room needs the command prefix (`!wa login`, and `!wa <answer>` for each reply); the bot says so when it happens. A fresh direct-message room with just the bot becomes its management room and needs no prefix.
- `login` on the mautrix-go bridges lists the flows. **WhatsApp**: `login phone`, then the number in international form, returns an 8-character pairing code the user types into WhatsApp (Linked devices → Link with phone number instead). **Signal**: `login` returns a QR code for Signal's Linked devices. **Meta**: `login messenger` (cookies from messenger.com) or `login messenger-lite` (username and password). **Slack**: `login email`, `login token` (token plus `d` cookie from a browser) or `login app`. **Discord**: `login-qr`, scanned from the Discord app's own Scan QR Code screen, not the phone camera; `login-token user <token>` is the fallback. **Google Messages**: no QR flow any more; `login` asks for the cookies of a signed-in messages.google.com tab — a devtools "Copy as cURL" of any request to it — then posts an emoji that the operator taps in Google Messages on the phone within a few minutes. The bridge redacts the pasted cookies from the room; `~/multichat/gmessages-login.sh` sends them from a terminal so they never pass through a chat. The phone must stay online, since texts travel through it. Pairing copies only `network.initial_chat_sync_count` chats (default 25; set to 1000 on 2026-10-01, which found 227), and only at a pairing or `relogin`, never at a restart. `~/multichat/gmessages-login.sh relogin` re-authenticates the existing login without an emoji and keeps every `@gmessages_…` id; a fresh `login` may not, and every contact link to a text contact would then point nowhere. Each chat keeps only about its last 100 messages: older history needs the backfill queue, which plain Synapse cannot take ("Matrix server doesn't support batch sending", measured 2026-10-01). The first pairing dropped by itself 12 minutes in (`gm-logged-out-401-polling`) with the browser session still signed in; the cause is unknown. **Telegram** (the pinned Python bridge): `login`, then the phone number, then the code Telegram sends to the user's app.
- ⚠️ **QR codes die in 45–60 seconds** — Signal makes a new one every 45 seconds as an edit of the same message, and Discord closes its login socket after 60. A code relayed through chat is dead on arrival: Signal says "network failed", Discord says "can't find that device". Show the live code on a page the user opens on a *second* screen (they cannot scan their own phone's screen), refreshed every few seconds, and restart the login on demand. Pairing codes and phone-number logins last a few minutes; start one only when the user is ready.
- `cancel` stops a pending login. `logout`, `list-logins` and `help` are on every mautrix-go bridge.

## How other services reach it

**dash** proxies a deliberate subset at `/api/multichat/*` (`dash/server/api_multichat.go`, `multichatProxiedRoutes`) for bridge-ui's Messages and Discord pages: the auto-reaction routes, `GET /contacts/unified`, `GET /conversations`, `GET /conversations/{room_id}/messages`, `POST /conversations/{room_id}/send`, `POST /conversations/{room_id}/send-file` (images and other files, with a caption), `GET /search`, the reaction routes, the tag routes, `GET /message-log`, `GET /discord/status`, media, and the emoji routes (`GET /emoji`, `POST /emoji/discord/refresh`, `PUT /emoji/favorites`, `PUT /emoji/settings`). **Since 2026-09-28 dash is multichat's web front end and a dash login can send into a conversation**; `POST /conversations/new`, `POST /messages/send` and the AI routes stay refused, and anything not listed is a 404 decided **before** a token is asked for. The token is resolved from auth-store provider `multichat` on each request, so a rotation needs no restart. **`~/bin/multichat-send`** resolves the same token from that provider using `AUTH_STORE_URL` and `AUTH_STORE_TOKEN`, which the scheduler unit gets from the drop-in `scheduler.service.d/multichat-send.conf`; disabled scheduler job 86 `multichat-send example` is the template to copy. **`~/bin/multichat-mcp`** is registered in tool-store as `multichat` (id 15), provisioned with a token from auth-store and opted in per instance on the bridge Tools page; permission-store rule `multichat-send-message-ask` makes `mcp__multichat__send_message` `ask` at global scope, so a human confirms each send. ⚠️ **That holds only in a session whose tool calls reach permission-store**: llm-bridge-server allows a session in `bypass` permission mode before any rule is read (noteboard todo `bfd3f4de-af8e-4e7e-8e52-0671a22cdf81`), so for an unattended session the real guard is that its instance has not opted in to this tool. **kanban-store's** message triggers send through `POST /api/messages/send` — see its row for why delivery is off by default. **Short names** — the typeable paths dash opens a chat at (`messages/kim`, `messages/nyc`, `messages/social/general`) — live in short-name-store (`SHORT_NAME_STORE_URL`, namespace `messages`, entity type `multichat_room`, the Matrix room id as entity id), and multichat chooses them, since it owns the facts about rooms: `POST /api/short-names/assign[?dry_run=true]` (`internal/shortnames`, details in `docs/api.md` under *Short names*) asks a model-store role (`SHORT_NAMER_MODEL_ROLE`, default `balanced`) through llm-bridge-server's `POST /oneshot` for a path for each conversation with no current name, most messaged first, checks every proposal in Go and writes those that pass. It leaves unnamed a conversation with no logged message and WhatsApp's status broadcast (`m.bridge` channel `status@broadcast`), which is no conversation, and never gives a group a bare first name that someone's direct message could use. It never renames a named room and never makes a name up in Go; a refused room waits for the next run. dash does not proxy the route. Scheduler job 108 `multichat short names` runs it hourly through `scripts/assign-short-names.sh`, which resolves the token like `multichat-send`; it was created disabled on 2026-10-20 for the operator to enable after reviewing a dry run.

# Working in this repo

## Build, test and deploy

Module `github.com/kayushkin/multichat`, with `replace` directives on `../bus` and `../llm-bridge`, so both sibling clones must be present to build. Seven binaries: `cmd/server` (the service, installed as `~/bin/multichat-server`), `cmd/multichat-send`, `cmd/multichat-mcp`, and four one-offs: `cmd/multichat-import-discord-archive` and `cmd/multichat-fetch-discord-history` (flags only), `cmd/multichat-backfill-reactions` and `cmd/multichat-backfill-room` (`-db`, `-room` for the latter, plus `SYNAPSE_URL` and `MATRIX_TOKEN`). `go build ./...` and `go test ./...` need no build tag. Deploy with `./deploy.sh`, which builds the binaries, checks the secrets, restarts the unit and asserts the 401 before reporting success. Pushes to `github.com/kayushkin/multichat`. **Every environment variable is declared in `internal/config`** (llm-bridge `servicesettings`): the server's twenty-two in `settings.go`, served at `GET /api/settings` behind the bearer, and the commands' own in `commands.go`. Nothing calls `os.Getenv`; a source-scan test fails on an undeclared read and holds each client to its own list. The server owns full names, never `MULTICHAT_` (`MULTICHAT_URL` is how other services find it), so `MULTICHAT_DB_PATH` stops the start and `MULTICHAT_URL` does not. `NATS_URL` without the Matrix client is refused in `config.Load`, and `deploy.sh` runs `TestTheLiveProcessEnvironmentBuildsARegistry` against the running unit's `/proc/<pid>/environ` before it installs anything.

## The database is pinned absolutely

SQLite at `~/repos/multichat/multichat.db`, pinned by `MULTICHAT_DB`. **SQLite does not fail on a missing file, it creates one**, so when `cmd/server/main.go` opened the bare relative path the database was wherever systemd happened to chdir: get the working directory wrong and multichat comes up with every route answering out of a brand-new empty database, looking perfectly healthy while the real contacts and tags sit untouched on disk. The absolute path removes the ambiguity, and `deploy.sh` refuses to deploy when the file named there does not already exist. `internal/db/sync_state.go` adds `matrix_sync_state` to the older tables in `internal/db/db.go`, and drops the retired `inbound_rules` and `inbound_dispatches`.

## Generated TypeScript types

`./generate-ts.sh` runs tygo per `tygo.yaml` and renders `internal/db/message_log.go` (`LoggedMessage`, `MessageReactionGroup`, `MessageLogPage`) `internal/db/emoji.go` (`EmojiCatalog`, `DiscordCustomEmoji`, `EmojiSettings`) and `internal/db/conversation_links.go` (`ConversationLink`) to `ts/db.ts` and `internal/discordbridge/status.go` to `ts/discord_status.ts`; the hand-written `ts/index.ts` only re-exports them, and the whole is published source-only as `@kayushkin/multichat-types`. Each output file gets a header naming the commit it was generated from. The Go structs are the source of truth — regenerate after changing a wire type rather than editing the render. tygo keeps one entry per Go package and renders every exported type in an included file, so a type that is not on the wire (`MessageLogFilter`, `ChannelLogCounts`, `LoggedReaction`) lives in a file that is not included (`message_log_queries.go`, `reaction_log.go`). **Only what another UI reads is rendered** — bridge-ui's Auto-reactions, Discord and Emoji pages, its emoji pickers and its conversation links — and bridge-ui's Messages pages keep hand-written types for the conversation routes, which are not rendered yet.
